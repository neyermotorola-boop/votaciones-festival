2. Introducción y objetivo

El Festival de la Leyenda Vallenata requiere una plataforma web donde el público pueda participar en votaciones organizadas por edición anual y por categoría (por ejemplo, canciones o baile). Este documento presenta los avances del proyecto: una aplicación web funcional, conectada a una base de datos MySQL, con autenticación de usuarios, un panel administrativo para cargar la información y una interfaz pública que muestra datos reales almacenados en la base de datos.

Objetivo general. Construir un sistema de votaciones configurable, seguro y auditable, que permita registrar ediciones del Festival, categorías vinculadas a cada edición, votaciones con sus opciones participantes y los votos de los usuarios autenticados.

Relación con el proyecto. Los avances cubren la estructura de datos esperada (Edición → Categoría → Votación → Opción), la futura incorporación de votos y sus restricciones (ya implementadas), la autenticación y las interfaces de administración y de consulta pública.

3.2 Arquitectura MVC

Una petición entra por routes/web.php, que la dirige a un controlador. Este consulta los modelos (que leen y escriben en MySQL mediante Eloquent) y entrega los datos a una vista Blade, que genera el HTML. Por ejemplo, al abrir /categorias/1 se ejecuta PublicoController@categoria, que carga la categoría con su edición y sus votaciones y renderiza categoria.blade.php.

3.6 Autenticación y autorización

  • Registro: validación de datos, aceptación del tratamiento de datos personales y contraseña guardada con hash.
  • Inicio y cierre de sesión: sesión con regeneración de identificador, opción "mantener sesión" y cierre con invalidación de la sesión.
  • Protección contra fuerza bruta: bloqueo de 5 minutos tras 5 intentos fallidos por correo e IP; el mensaje de error no revela si el correo existe.
  • Roles: administrador y votante. El middleware EsAdmin impide que un votante acceda al panel (respuesta 403).
  • Bitácora: se registran los inicios de sesión y las acciones administrativas.

5.1 Migración de la tabla votos

database/migrations/2026_10_24_193951_create_votos_table.php 
Schema::create('votos', function (Blueprint $table) {
    $table->id();
    $table->foreignId('user_id')->constrained()->cascadeOnDelete();
    $table->foreignId('votacion_id')->constrained('votaciones')->cascadeOnDelete();
    $table->foreignId('opcion_id')->constrained('opciones')->cascadeOnDelete();
    $table->timestamps();
    // un usuario no puede votar dos veces por la misma opción
    $table->unique(['user_id', 'votacion_id', 'opcion_id']);
});

Las llaves foráneas garantizan la integridad referencial y la restricción única evita votos duplicados a nivel de base de datos.

{

}

5.6 Regla central: registrar un voto

app/Http/Controllers/PublicoController.php 
$error = DB::transaction(function () use ($votacion, $datos, $user) {
    // Bloqueo para evitar votos duplicados concurrentes.
    $votacion = Votacion::whereKey($votacion->id)->lockForUpdate()->first();

    if (! $votacion->estaAbierta()) {
        return 'Esta votación no está abierta.';
    }
    $opcion = Opcion::where('votacion_id', $votacion->id)->find($datos['opcion_id']);
    if (! $opcion) {
        return 'La opción no pertenece a esta votación.';
    }
    if (Voto::where('user_id', $user->id)->where('votacion_id', $votacion->id)->count()
            >= $votacion->votos_por_usuario) {
        return 'Ya alcanzaste el máximo de votos permitidos en esta votación.';
    }
    if (Voto::where('user_id', $user->id)->where('opcion_id', $opcion->id)->exists()) {
        return 'Ya votaste por esta opción.';
    }

    Voto::create(['user_id' => $user->id, 'votacion_id' => $votacion->id, 'opcion_id' => $opcion->id]);
    return null;
});

9. Conclusiones y distribución del trabajo

9.1 Aprendizajes

  • Un modelo de datos jerárquico (Edición → Categoría → Votación → Opción) permite reutilizar el sistema en cada edición del Festival sin cambiar el código.
  • Las migraciones y los seeders hacen el entorno reproducible; Docker permite que cualquier integrante o el docente lo levante con un solo comando.
  • Las reglas críticas (un voto por opción, límite por usuario, votación abierta) deben validarse en el servidor y respaldarse con restricciones en la base de datos y transacciones.
  • Separar roles y proteger rutas con middleware mantiene la administración fuera del alcance del público.

9.2 Dificultades

  • Adaptar la ruta sugerida (Django) a Laravel, equivalencia acordada con el docente, manteniendo los mismos conceptos y entregables.
  • Configurar la conexión entre los contenedores de la aplicación y de MySQL, y esperar a que la base esté lista antes de migrar.
  • Evitar votos duplicados cuando varios usuarios votan al mismo tiempo (resuelto con transacciones y bloqueo).

9.3 Pendientes

  • Validar con el cliente el texto legal de tratamiento de datos, la categorización definitiva y las reglas marcadas como pendientes.
  • Recuperación de contraseña y verificación de correo electrónico.
  • Carga de imágenes para las opciones (el campo existe en la base de datos).
  • Despliegue en un servidor de producción con credenciales propias.
